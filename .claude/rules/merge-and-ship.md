# 合码与 Ship 铁律

## 合码必须等用户确认

合并 PR 前必须等用户明确说"合"或"merge"，不得自行判断"改动小可以直接合"。
无论改动大小，包括"只改了文档/配置"的情况，执行 `ghc pr merge` 前都要先告知用户 PR 内容并等待明确许可。

## Ship 前必须列出所有改动

1. **不允许遗漏提交**：ship 前必须列出分支上的所有 commit 和改动文件清单。如果有意料之外的文件改动（如 Makefile、基础设施文件），必须向用户确认是否一起合入，不能擅自跳过。
2. **合并冲突必须用户确认**：rebase/merge 产生冲突时，必须先展示冲突内容给用户，让用户决定怎么解决，不能自行选择版本。基础设施文件的冲突解决如果选错版本会影响部署。

## 禁止上线线上用不到的逻辑

1. **禁止基于具体泳道名的 hardcode 判断。** 代码里不允许出现「当前泳道是不是 `coe-xxx` / `ppe-xxx`」这类判断来决定功能开不开、哪套实现被注册。泳道是部署位置，不是功能身份。
2. **线上所有可选功能必须可动态配置。** 开关走 Dynamic Config，运行时可改、可回滚，不需要改代码重新发版。把开关写死成源码常量 = 每次切换都要发一版，而且回滚也要发一版。
3. **禁止合并 prod 永远走不到的逻辑。** 一个功能如果按当前代码在 prod 上不可达，它就不该进 main。「先把代码合了，启用以后再说」是把工作做了一半，不是上线。

违反的典型形状：为了"保护 prod 不被实验代码影响"而在源码里写死一个实验泳道名，让整套新实现只在那条泳道注册。这道门从写下的第一天起就是注定要被拆的东西，而拆它要改代码、发版、重新验证。

## 上线节奏由用户定，不由 AI 制造紧迫感

1. **禁止拿 commit 数量、分支存活时间、"再拖会更难合"当理由推动上线。** 本仓库单人维护，main 上没有第二个人在推进，分支挂多久都不会产生合并冲突——这个紧迫感是假的。
2. **功能全部开发完毕才上线，不是开发一点上线一点。** 除非用户明确要求分批上。
3. **冷启动不是上线阻塞理由。** 新系统在 prod 上没有历史数据是它的正常初始状态，不拿它当"还不能上"的论据。

## 推理时不要套用不成立的前提

1. **说出「难合」「发布节奏」「影响面」「灰度」「隔离」这类词之前，先验证这个担心的前提在本仓库成立。** 团队协作项目的默认假设不自动适用：这里单人维护，prod 上的用户就是作者本人，没有并行分支冲突、没有第三方用户要保护、没有发布窗口要协调。
2. **读到既有设计时，先问它该不该存在，再核它写得对不对。** 论证详尽不等于前提正确；一段只论证「该怎么写」的注释，证明不了「该不该有」。
3. **禁止拿本会话或过往会话自己写的 spec / 文档当客观约束**去论证某件事不能做。范围是当时划的，写它的人就是用户和 AI 自己，可以改。
