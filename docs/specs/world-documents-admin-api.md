# 从外部读写世界的文档树

状态：已定稿（2026-09-20，经两轮外部评审）

## 目标

让 bezhai 能从外部读、写、删 world 那棵文档树上的任意一份文档，并且不绕开 world 已有的写入安全——每份文档一把锁，整份重写和删除必须带上读到那一份时的指纹。

外部写入和 world 是**对等的两个写者**。谁也不比谁高一级，谁也不阻塞谁，冲突由指纹暴露出来让后写的那一方重读。

## 不做什么

- **不做 UI。** 只做 API。
- **不做"单处替换"那只手。** world 有它，是因为模型要在不重读全文的情况下改一个词。人手里有全文，整份重写够用。少一种手就少一套并发语义要解释——那只手靠唯一命中做 CAS，跟指纹是两个模型。
- **不改 `设定/` 的归属。** world 仍然能写它。这是明确选过的：两边都能写，靠指纹挡冲突。
- **不让第二个服务挂上文档树那个卷。**
- **不解决"world 不读 `设定/`"。** 那是改它每轮的输入，是另一条线。这组接口让人能写进去，但写进去之后 world 看不看得见，本 spec 不负责。

## 现状与根因

### 树写歪了没有任何外部修正途径

这棵树只有一个写者入口：world 的五只手。树上任何一份写错的文档——地名写成繁体、同一个地方两个名字、设定写得不对——只能等 world 自己发现自己改。人插不上手。

已经发生过的形状：`地方/家/客廳.md`、`地方/家/我的房間.md`（写了三次）、`家/走廊.md` 和 `家/楼上/走廊.md` 并存。这些后来被 world 自己清掉了，但那是运气，不是机制。

### `设定/` 已经是只写不读的死枝

能查到的每一次读都落在 `事/` 和 `地方/`，一次都没读过 `设定/`；能查到的每一次写都落在 `地方/` 和 `事/`，一次都没写过 `设定/`。而读到的正文跨轮会被抹掉，所以就算读过也记不住。

世界坐落在哪座城市写在 `设定/` 里。world 看不见它，于是那几只看真实世界的手说不出城市名，一次都没用过。

**这解释了为什么需要先能读。** 那份文档的正文现在没有任何人看得见——包括写它的人。

### 文档树那个卷只有一个挂载点

文档树的卷是 `pvc-world-docs`，只挂在 agent-service 上（可写）。开发机读不到，节点上也找不到落盘路径。

这个"只有一个挂载点"不是偶然，它是文档树**没有**做 fd 逐段打开 + `O_NOFOLLOW` 的前提之一：只有一个写者能碰这个卷，符号链接就没有第二个来源。历史上这棵树曾和另一个卷共用，另一个服务把同一个卷根挂成可写，那个服务的文件 CRUD 就能直接改到这棵树，后来迁到独立卷才堵上。

**说法要精确到 PVC 名。** monitor-dashboard 现在就挂着一个可写卷（`pvc-shared-skills`，给 skills 用），所以"dashboard 不挂卷"这句话本身已经不成立——挂卷对它不是技术障碍，它天天在挂。成立的是"**没有第二个服务挂 `pvc-world-docs`**"。这条差别在评审时极容易被当成天然前提滑过去，所以本 spec 里凡是涉及这条约束的地方一律写 PVC 名。

## 关键设计决策

### 一、接口必须由跑 world 的那个进程执行

写入安全用的是两把进程内的锁：一把 asyncio 锁让协程排队并给出超时上限，一把线程锁覆盖真正碰盘的那一段（协程被取消时线程锁放不开，而 asyncio 锁会放开——这正是它存在的理由）。

外部写入只要在**同一个进程**里走同一条加锁路径，抢的就是 world 五只手真正碰盘时抢的同一把 per-file 锁。粒度一致，不需要新增任何协调机制。

换任何别的进程去写那个卷，这两把锁立刻失效，指纹 CAS 也跟着变成摆设——因为读和写之间不再有共同的锁，"读到指纹 → 带着它写回"中间可以插进任意多次别人的完整写入。

**推论：dashboard 只能转发 HTTP，不能挂 `pvc-world-docs`。** 挂上去会同时打掉锁和上面那条"只有一个挂载点"的前提。

### 二、泳道靠 header 选，不靠参数

树的根是 `$WORLD_DOCS_DIR/<泳道>`，泳道那一段由进程按自己的部署环境拼出来，不读请求上下文。

所以接口里**没有任何地方能指定泳道**：请求被送进哪个 pod，动的就是哪棵树。选泳道靠的是把请求路由到哪个 pod，不是参数。

理由沿用文档树现有的那条：靠参数选泳道的话，一次写错就直接改到 prod 的设定集，而这件事没有报错，也没有备份可以退回去。

### 三、结果和措辞必须分开

写入和删除现在的返回值是**写给模型看的中文句子**，成功和各种拒绝都是句子。

HTTP 调用方没法从句子里机器可读地分辨"写成功"和"指纹过期被拒"，除非去解析中文——那是脆的，而且会在措辞改动时静默失效。

而这一侧的整个契约就是"靠指纹挡冲突"。**分不清冲突就等于这一侧的契约不可用。**

所以结果要先成为一个结构化的东西，模型那一侧的句子和程序那一侧的字段都从它渲染出来。一处定义，两种呈现。这不是为将来抽象——是因为现在真的出现了第二个受众。

### 四、鉴权：现在是零，而这次的后果不一样

agent-service 目前没有任何鉴权分支，现有的运维路由也是裸的，而它的路由前缀整段对外可达。

现有裸着的端点最坏是重投一批死信。**一个能删掉地方文档的端点裸着不是一个量级**：那份文档的正文是原样塞进三姐妹眼前的，删掉之后她走进那个地方什么都看不到，而且不会有任何报错。

dashboard 那一层自带鉴权和审计，但**它挡不住直接访问**——服务的路由前缀本来就整段可达，绕过 dashboard 直接打是通的。所以这是两件事，都要做：

- **门在 agent-service 自己身上**：新增路由校验 token。
- **dashboard 提供带审计的入口**：写操作留下调用者、路径、泳道。

只做后者等于没有门，只做前者等于没有账。

### 五、落到哪棵树，必须由执行侧自报

既然选了靠路由选泳道，就得回答一个问题：调用方怎么知道自己刚才改的是哪棵树？

现在的答案是不知道。泳道不在注册表里时请求静默落 prod 并返回 200——对调用方来说，这和送达成功长得一模一样。而这组接口的每一次写入都是不可逆的：这棵树没有版本历史，没有备份。

所以**每个响应都要带上实际执行它的那个进程自己的泳道**，由调用方比对。这个值必须由执行的进程从自己的部署环境里读出来，**不能回显请求里的任何东西**——回显请求等于什么都没验。

这不是给人看的调试信息。它是"这次调用改的是我以为的那棵树"的唯一证据，A4 那条验收整个建立在它上面。

## 调用方与影响面

- **新增路由**，不改现有路由的行为。
- **改动写入与删除的返回类型**，波及 world 的五只手和它们的测试。这是本次唯一碰到既有写入路径的地方。
- **dashboard 新增一组转发端点、一个新的出站 client、一个新环境变量和对应的审计动作名。**
- **monitor-dashboard 新增一个 ConfigBundle 引用**（`inter-service-auth`，为了拿 `INNER_HTTP_SECRET`——它现在没有）。这是**部署期变更、影响线上**，动之前要单独跟 bezhai 确认，不随本 spec 自动获得授权。
- **会碰一处既有审计代码**：dashboard 那个塞结构化审计字段的 Variables 键名现在叫 `gatewayAudit`，新端点要复用它，语义已经外溢，顺手改成中性的名字。这是本次唯一碰到既有审计路径的地方。
- **gateway 规则不动**——服务的路由前缀规则已经存在，新路径自动命中。
- 无 DB schema 变更，无 prompt 变更，无 Dynamic Config 变更。

## 硬约束

### 单副本是前提

两把锁都是进程内的。多副本部署下它们拦不住跨进程的写者。这不是本次引入的，是文档树本来的前提，但这组接口让"同一个进程"从一句实现细节变成了对外契约的一部分——写下来，别哪天顺手扩副本。

### 路径穿越的判定不能照抄别处

同一个仓库里另一处的文件 CRUD 用字符串前缀判定路径是否在根内，那是错的：根是 `/data/world` 时 `/data/world-evil` 会被判成在根内。文档树自己用的是父目录包含关系。新接口复用文档树现有的那一套，不新写。

### 泳道路由会静默落回 prod

请求能否被送进指定泳道的 pod，取决于两件运行态的事：网关那个 App 有没有注入 sidecar（已查证为开，但那是运行态配置，不是代码事实），以及目标泳道当时在不在泳道注册表里。

**第二件是会咬人的那件**：泳道不在注册表里时，sidecar 把原始 host 原样返回，请求于是落到 prod 的 pod 上——没有报错，调用方拿到的是一个正常的 200。所以"带了泳道 header"不等于"到了泳道"，而这组接口一旦落错地方，改的就是 prod 的设定集。

所以它单独成为一条任务，且必须在功能验收之前完成；验收口径必须是"两棵不同的树"，不能是"请求成功"。

## 未决

0. **dashboard 里那两个打 agent-service 的转发端点是死的**（本次调研顺带发现，不在本 spec 范围）：它们把 `/api/agent/admin/trigger-diary` 这类路径发给 paas-engine 的地址，而 paas-engine 并不代理 `/api/agent/`；agent-service 那侧也没有对应的路由。没人报过，说明没人用过。要不要修另说，但它意味着**仓库里没有一个能用的 dashboard → agent-service 范例**，A5 是第一条。
1. **读出正文之后，`设定/世界底子.md` 到底要不要改、改成什么**——这得先看见它才能决定，不在本 spec 范围内。
2. **`人/` 里没有主人、`地方/` 里没有他的位置**，这是这一版引擎的设计缺口（早先那版世界模型把他定成一个有位置的特殊角色，现在的引擎没实现）。这组接口让人能往树上写他，但"他在这个世界里是什么"是设计问题，不是接口问题。

## 任务清单

> 只写目标 + 产出 + 验收口径。实现细节在动手时基于实际改动生成。

**A1 · 结果和措辞分离**
目标：写入与删除的结果不再只以中文句子的形式存在。
产出：结构化结果，加上两种呈现——模型看的句子、程序看的字段。
验收：
- 模型那一侧收到的**完整结果逐字不变**——不只是那句中文，还包括错误包装之后附带的每个字段（异常类名会经由包装器进入模型的上下文）。
- 这条必须用**独立基线**来验，不能用"现有用例不改断言即通过"：现有那几个冲突用例的断言很弱（只检查返回类型、只检查是否包含某个子串），中文一字不改而异常类名变了，它们照样全绿。做法是在动实现之前先捕获改前的完整模型可见结果（成功分支 + 每个拒绝分支，序列化之后的完整结构），写成钉死内容的用例，改完必须仍然逐字绿。
- 基线的期望值写成字面量，**不能从实现自己的枚举或常量推导**——那样收窄实现的同时也收窄了期望值。
- 新增用例断言程序那一侧能分辨这四种结果：成功、缺指纹、指纹过期、目标已被删。
前置：无。

**A2 · 文档树的外部端点**
目标：从外部能读、写、删这棵树上的任意一份文档。
产出：列目录、读一份、整份重写、删除四个端点，复用现有的锁与指纹，不新增第二条写入路径。
验收：
- 必须证明外部写入和 world 的轮次抢的是**同一把锁**——构造 world 持锁期间的外部写入，断言它排队等待而不是并行写盘。只断言"两个 HTTP 请求串行"不算，那证明不了跨写者。
- 必须证明指纹语义与那五只手一致：不带指纹覆盖已存在的被拒、带过期指纹被拒、删除不带指纹被拒、目标已被删但带了指纹被拒。
- 路径穿越、空字节、指向根之外的路径被拒。
- **正向路径必须单独验**：新建一份文档 → 读回来核对正文与指纹 → 拿正确指纹整份重写 → 读回来确认真的改了 → 拿正确指纹删掉 → 确认删了。这条是专门挡"全部拒绝也能全绿"的：上面那些验收全是拒绝场景，一个永远返回拒绝的实现能通过它们中的每一条。
前置：A1。

**A3 · 门**
目标：这几个端点不再是裸的。
产出：凭据校验，只覆盖新增路由。
凭据用 **`INNER_HTTP_SECRET` + `Authorization: Bearer`**：agent-service 已经通过 `inter-service-auth` 拿得到它，不需要新增任何配置；仓库里内网互信的既有口径就是这个 Bearer，换别的等于开第二套。
两条已经查证过、必须在实现里避开的形状：
- **未配置时 fail-closed 全拒，不是全放。** agent-service 现有那两处用它的地方都是出站（`if secret:` 没配就不带头），那是出站的正确姿势；照抄到入站就等于没有门，而且是没有报错的那种。
- **范围限制必须在结构上成立，不靠路径白名单判断。** 这个服务的路由是自动注册的，挂全局中间件会顺手盖住 `/health` 和 DLQ 那几条——正好撞上下面那条验收。让新路由自己带上校验，而不是让校验去认路径。
验收：**带正确凭据放行**（同理，一个全拒的门能通过下面每一条）；不带凭据被拒；带错凭据被拒；未配置凭据时**全拒**；**现有的 health 与运维路由行为逐字不变**（这条容易被顺手扩大，要有用例钉住，且用例不能用实现自己的前缀常量去选路由——那样收窄实现的同时也收窄了测试）。
前置：A2。

**A4 · 泳道可达性与落点自报**
目标：确认请求真的能被送进指定泳道的 pod，以及落错地方的时候调用方能发现。
产出：真实调用证据，不是单测。
验收：
- 带泳道 header 调用，响应自报的执行泳道**等于**请求的那条泳道。
- 带一条**不存在的泳道**调用，响应自报的执行泳道是 prod——证明落回确实会发生、而且看得见——并且确认这次调用**没有改动 prod 的任何文档**。
- **不能靠比较两次返回的正文来判断"是两棵树"。** world 随时在改文档，两次正文不同证明不了任何事，两次相同也证明不了任何事。判据只有执行侧自报的身份。
排序：必须在 A3 之后（新端点带着门，对外调用要凭据）、A6 之前。
失败的影响范围：A4 不过，作废的是依赖真实路由的那部分验收（A6），**不作废 A2 的锁与指纹测试**——那些是进程内的事实，跟路由无关。

**A5 · dashboard 入口**
目标：这组操作有带审计的入口。
产出：转发端点、一个新的出站 client、审计动作名。
三条已经查证过的实现约束：
- **dashboard 现在没有 `INNER_HTTP_SECRET`**，要把 `inter-service-auth` 加进它的 ConfigBundle 引用。这是影响线上的部署期变更，单独确认后才能动。
- **泳道走 header 透传**，把 `x-lane` / `x-ctx-lane` 归一成 `x-ctx-lane` 交给 sidecar 选路（dashboard 里已有这个小函数，但有两份拷贝，顺手收成一处）。**不要照抄 `?lane=` 那种写法**——那是拿泳道当控制面查询参数，不是选路，用在这里会让请求永远落在 prod。
- **审计不存文档全文。** 审计中间件默认把整个请求 body 写进记录里，而整份重写的 body 就是文档正文（上限 12000 字）。审计要回答的是"谁、什么时候、改了哪一份、从哪个指纹改起"，不是"改成了什么"；全文版本历史是文档树自己的缺口，不该靠审计表兜出来。handler 要把落进审计的 body 覆盖成路径、泳道、指纹、长度。
关于"审计里没有正文"这条，有一个已经查证过的形状必须避开：审计中间件是**在 handler 之前读走 body、在请求结束时落库**的。所以只在 handler 里覆盖 body 不够——参数校验提前返回、上游超时、上游抛异常，这几条路径都发生在覆盖之前。而且正文还能从另外两个通道漏进去：查询串，以及错误消息。具体在哪一层排除留给实现阶段决定，但验收要覆盖全部分支。
验收：写操作在审计日志里留下调用者、路径、泳道、指纹；**成功、参数被拒、上游拒绝、上游超时这几条路径最终落库的整条记录里都没有文档正文**（用一段独立的正文标记串去验，不是看一眼）；**dashboard 没有挂 `pvc-world-docs`**（要有证据，不是声明）。
前置：接口契约定下来即可开工，**不必等 A3 做完**；联调依赖 A3。

**A5b · 给 dashboard 注入凭据**
目标：dashboard 拿得到打这道门所需的凭据。
产出：把 `inter-service-auth` 加进 monitor-dashboard 的 ConfigBundle 引用并重新部署。
验收：dashboard 的解析后配置里出现该凭据。
**这是影响线上的配置变更，单独走一次确认，不随本 spec 自动获得授权。** 它是一个独立的部署检查点，不混进 A5 的代码交付。
前置：无（但 A6 依赖它）。

**A6 · 真的改一次**
目标：证明这条链路端到端可用，并且回答最初那个问题。
产出：读出 `设定/世界底子.md` 的正文。
验收：
- 正文被读出来并贴在验收记录里——这是本 spec 的起因，读不出来就等于没做。
- **完整走一遍写入**：通过 dashboard 读出一份文档的正文与指纹 → 拿这个指纹整份重写 → 读回来核对内容真的变了 → 拿新指纹删掉一份测试文档 → 确认删了。
- 在一份 world 会动的文档上构造一次**真实冲突**：外部读到指纹 → world 改了它 → 外部拿旧指纹写回被拒，**并且确认被拒之后那份文件没有被改动**。这是"两边都能写、靠指纹挡冲突"唯一的真实证据，替身构造的不算。

## 为什么这么选

**为什么不让 dashboard 直接读写 `pvc-world-docs`**——那是最短的路，一个服务就够了，而且 dashboard 已经在挂别的可写卷，技术上没有任何东西拦着它。正因为没东西拦着，这条才必须写成约束。它同时打掉两样东西：进程内那两把锁（于是指纹 CAS 失效），以及"这个卷只有一个挂载点"（于是文档树里那段"不需要 fd 逐段打开"的推理作废）。省下的是一跳 HTTP，赔进去的是写入安全本身。

**为什么不把锁沉到跨进程**——真要多个进程写同一棵树，正确做法是换带 CAS 的存储或者做 leader election，不是把现在这两把锁改造成分布式锁。而本次根本不需要多进程：外部写入完全可以由同一个进程执行。

**为什么不给接口加泳道参数**——这是一个设计取舍，不是技术必然。这个位置上先后写过两条论证，都被独立核对推翻了，记在这里免得再写第三遍：

- ~~"路由是部署事实，写不错"~~——错。泳道不在注册表里时请求静默落 prod，而且注册表是持续刷新的，这不是部署期一次性的事。
- ~~"参数方案在当前挂载结构下根本实现不出来"~~——也错，或者至少代码证明不了。部署器直接用 App 配置里的 PVC 和 SubPath，没有按泳道自动隔离挂载；"进程拿不到别的泳道的路径"这句话在仓库里找不到支撑。

真正的理由只有一条，而且它是取舍不是必然：**参数把"改哪棵树"变成每次调用都要写对的东西，路由把它变成部署期定死的东西。** 两种都会错。选后者的代价是必须另外有一条机制让调用方知道自己实际落到了哪棵树上——见关键设计决策第五条。

这三次的共同形状值得单独记一笔：每次都是把一个取舍包装成"不可能"，而包装用的那个前提没有被核对过。
